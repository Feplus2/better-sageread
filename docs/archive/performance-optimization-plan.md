# 前端性能优化专项计划（2026-08-07）

> 状态：P1 实施中 / P2、P3 待排。本文档记录诊断实测数据与三个方案的设计、实施顺序、验收标准。
> 原则：这是产品交付前的正式优化，不是急救——三个方案都做，稳步推进。

## 一、诊断记录（实测数据）

### 1.1 Agent 工具调用期内存风暴（已修复）

- 现象：Agent 执行多轮工具调用期间渲染进程内存 1.3GB → 4.7GB，主线程被渲染占满，任务结束后不回落。
- 机制：流式更新每 50ms 一次 → 全量重渲染所有消息（Markdown 重解析 + 工具卡重建）→ V8/Blink 内存竞技场膨胀。
- 已实施修复（2026-08-07）：
  1. 工具输出展示截断（>4000 字符）；
  2. `chat-messages.tsx` 渲染单元 memo 化（MemoizedMarkdownContent / MemoizedReasoningContent / MemoizedTool，依赖 ai@5 useChat 历史消息引用稳定的架构事实）；
  3. `onViewToolDetail` 回调 useCallback 稳定化（两处调用点）。
- 验证：修复后同类任务内存峰值 4.7GB → 1.7GB。
- 残余问题：渲染 DOM 仍随消息数线性累积，无卸载机制——见方案 P3。

### 1.2 设置页打开卡顿（多轮实测，含一次误判修正）

- 现象：打开任意 Radix 对话框（含设置）需约 7-8 秒，**与聊天页是否在前台无关**。
- **误判修正（诚实记录）**：第一轮 CPU Profiler 看到 `focus` 占 3s，曾归因于 Radix 焦点扫描并尝试 `onOpenAutoFocus preventDefault`——**实测无效（仍 6.8s），已回退**。焦点不是大头。
- **真实根因（重抓栈 + DOM 审计锁定）**：
  - 打开对话框时触发**全页样式/布局强制重算**：Profiler self-time 大户是 `get scrollTop`(2.8s) + `getAnimationName`(2.7s)，两者都是读布局/样式属性引发的整页回流。Radix 打开时锁 body 滚动（改 body 样式）使全文档样式失效，随后读 scrollTop/animation-name 强制回流。
  - **为什么回流这么贵**：DOM 审计显示干净状态下全页 5.3 万元素中有 **3.57 万个 `<span>`，其中 2.45 万聚集在单个 `prose` 容器里，class 全是 KaTeX（vlist/mord/pstrut/msupsub）**——即 DF 对话里大量数学公式被 KaTeX 全量渲染成海量 DOM。对话越大公式越多，DOM 越大，回流越慢。
  - 结论链：**对话消息（尤其含大量公式的）无窗口化全量渲染 → DOM 巨大 → 打开任何 Radix 对话框触发整页强制回流 → 7-8 秒**。
- 排除项：背景视频+磨砂层（暂停后仍卡）、CSS 规则规模（全页仅 762 条）、Radix 焦点扫描（preventDefault 无效）。

## 二、方案总览（按修正后的优先级）

> 诊断修正后的结论：本案的大头是**对话消息 DOM（尤其 KaTeX 公式）**，不是阅读 tab。因此 P3（消息窗口化）优先级提到最高。P1（焦点）已被证伪回退，不再作为独立方案。

| 编号 | 方案 | 性质 | 工程量 | 顺序 |
|---|---|---|---|---|
| P3 | 聊天消息尾部窗口 + 上滑渐进加载 | 治本（消息 DOM 封顶，本案大头） | 中 | 1 |
| P2 | 标签页休眠/懒挂载 | 治本（消灭阅读 tab 常驻 DOM） | 中 | 2 |
| P4 | 公式/重消息懒渲染（KaTeX 按需渲染） | 深度优化（单条重消息的 DOM 也能封顶） | 大 | 3（可选，视 P3 效果） |

## 三、P3 聊天消息尾部窗口 + 上滑渐进加载（核心修复，优先）

### 设计取向

纯可视区虚拟化（react-window 式）对变高消息（Markdown/工具卡/代码块高度不可预知）测量复杂、滚动锚定易跳，不适合本场景。
采用**尾部窗口 + 上滑渐进加载**（主流聊天应用通行模式）：

- 默认只渲染**最近 N 条**消息（N=50，窗口大小可调）；更早的消息不渲染，顶部渲染一个占位行（"还有 n 条更早消息"）。
- 用户**上滑接近顶部时自动扩展窗口 +N**（保持视口内容不跳：记录扩展前后 scrollHeight 差值补偿 scrollTop），也可点击占位行手动加载。
- 流式输出期间窗口恒含最新消息，零影响；新消息到来自动滚动逻辑不变。
- **选择模式（多选导出）进入时临时扩展为全量渲染**（导出依赖全量消息数据——数据层不受窗口影响，仅选择 UI 需要全量可见）。
- 搜索/跳转类功能若未来引入，以消息 id 定位 + 强制扩窗至目标位置。
- 注：针对"只渲染可视区太短"的反馈，尾部窗口 N=50 是一个合适大小的缓冲窗口（远大于可视区），兼顾流畅与上下文可见性。

### 数据结构

- `messages` 数组保持全量（数据层不动）；渲染层维护 `visibleCount` state（初始 N，向上扩展 += N，直到全量）。
- 渲染切片 `messages.slice(max(0, len - visibleCount))`；占位行显示剩余条数。
- 切换对话时 `visibleCount` 重置为 N。

### 验收

- 构造 300+ 条消息的对话：打开/滚动流畅，渲染 DOM 消息节点 ≤ 窗口大小 + 余量；
- 上滑扩展无跳动；多选导出在扩展全量后结果完整；
- 流式输出、停止、重试、工具卡展开等既有交互无回归；
- 复测打开设置页：longtask 从 6-7s 级显著下降。

## 四、P2 标签页休眠/懒挂载

### 现状

`reader-layout.tsx`：所有 tab（foliate 书籍视图 + 论文视图）常驻挂载，仅 `visibility:hidden` 隐藏。内存/DOM 随开过的 tab 数线性增长。

### 设计

- 每个 tab 记录 `lastActiveAt`；非活动 tab 超过阈值（默认 10 分钟，可配置）后**卸载视图 DOM**，保留 `readerStores` 中的阅读状态（进度/位置/设置，zustand 独立 store，天然支持重挂载恢复）。
- 切回时按 store 状态重挂载恢复（foliate 按存储的 location 恢复位置）。
- 阈值内切换行为不变（零加载成本）；超时后切回有一次内容加载成本（可接受，换长期内存上限）。
- 风险点：
  1. foliate 重挂载 + 已知 `el is null`（隐藏 tab 过早渲染）问题在重挂载路径可能放大——需一并验证；
  2. 论文 tab 结构简单，**先在论文 tab 验证模式，再推广书籍 tab**。
- 上限保险：即使阈值未到，同时挂载的视图数超过上限（如 6）时，最久未活动的先休眠（LRU）。

### 验收

- 打开 5+ 个 tab 静置超阈值后，renderer 进程 Nodes/内存显著下降（对比基线 >50%）；
- 切回休眠 tab：阅读位置精确恢复，无白屏/崩溃；
- `el is null` 不复发（含隐藏→快速切回场景）。

## 五、P4 公式/重消息懒渲染（深度优化，可选）

### 背景

诊断发现单条重消息（含大量 KaTeX 公式）即可产生 2.4 万个 span。P3 窗口化封顶了"消息条数"，但单条重消息的 DOM 依然可观。P4 进一步对重消息做懒渲染。

### 设计取向（待 P3 落地后评估是否需要）

- 对含大量公式/超长内容的消息，仅在滚入可视区附近时才渲染 KaTeX（IntersectionObserver 懒挂载），滚出后可折叠为占位。
- 或限制单条消息 KaTeX 渲染数量上限，超出部分懒加载。
- 工程量较大且与 Markdown/KaTeX 渲染管线耦合深，列为可选，视 P3 落地后的实际效果决定是否实施。

### 1.3 公式分布审计（2026-08-08，持久探针复测，修正 1.2 归因）

复现场景：52945 元素 / 35734 span（与 1.2 一致）。新探针补齐了 1.2 缺失的"公式个数"证据：

- **公式实例数 1139**，avg=30 span/公式、median=19、max=393 —— KaTeX 本身无异常，无重复渲染 bug。
- **挂载位置定位：1133/1139 在论文阅读器视图**（DIV[root] 容器，论文 oxygen-redox-chemistry… 的译文），聊天消息仅 4 个。⚠️ 1.2 中"DF 对话公式"的归因需修正：**重 DOM 大头是论文译文全量渲染，不是聊天**。
- 公式构成：唯一 TeX 仅 375 个，大量是化学下标类微型公式（`_{2}` ×119、`_{3}` ×35…），每个再小的公式也付 ~40 元素固定开销。
- **MathML 无障碍层浪费**：math/semantics/annotation/mi/mrow/mn/msub 合计约 1.3 万元素，占全页 24.5%，为 KaTeX 默认隐藏 MathML 输出（屏幕阅读器用）。

### 1.4 由此产生的候选快赢与优先级重评

- **候选 P0（快赢，待验证）**：KaTeX 输出改 `output: 'html'` 关掉 MathML 层，一行配置减 ~25% 全页 DOM。
  风险：paper-blocks/paper-reader 的对齐高亮逻辑注释强调"textContent 结构与 rehype-katex 一致"，关 MathML 会改变 `.katex` 的 textContent（默认下 MathML+HTML 文本双份）——必须先验证对齐/划词/高亮链路不回归；另损失无障碍语义（桌面阅读器场景影响小）。
- **P3 重评**：聊天侧实测仅 12 条消息挂载、DOM 占比极小，"聊天消息窗口化"不再是本案大头；若仍做，理由变为"预防未来长对话"而非治当前卡顿。
- **新候选 P5**：论文译文视图的块级虚拟化/懒加载（论文块结构天然适合），替代 P3 成为治本方向。

### 1.5 决定性实验（2026-08-08，摘除对比法，因果链实锤）

实验（.tmp-decisive2-probe.mjs）：把 span>1000 的 prose 容器临时摘出 DOM 后重测开设置耗时：

| 组 | DOM 规模 | 开设置耗时 | 最长 longtask |
|---|---|---|---|
| 对照（原样） | 52945 | 6138ms | 5991ms |
| 实验（3 个论文 prose 容器摘除，35130 span） | 2849 | **1256ms** | 1109ms |

结论：
- 卡顿元凶确认为**论文译文视图的 3 个 prose 容器**（24451 + 6832 + 3847 span），与聊天无关。
- 机制澄清：非 React 反复重渲染（memo 后 React 侧已稳定），而是**弹层打开瞬间的全页强制样式重算/回流**——弹层挂载 + body 滚动锁定 + 读 scrollTop/animation-name 触发，成本随 DOM 规模线性增长。滚动/悬停走合成层不受影响，故"滚动顺、开弹层卡"。
- 残余基线：2849 元素时仍需 1.2s（Radix 挂载/动画 + dev 构建开销），生产构建应更低。
- 新发现：同一论文同时挂载了 3 个重型 prose 容器（原文/译文/对照类），非活动视图的 DOM 参与回流——与 P2 标签页休眠同源，可合并处理。

### 1.6 CSS 手段 A/B 评估（2026-08-08，scripts/cdp-perf-css-ab.mjs，无侵入注入实测）

每组 2 次试验，前后各带基线漂移检查（基线三次均稳定在 5750-6275ms，无漂移）：

| 手段 | 开设置耗时 | 结论 |
|---|---|---|
| 基线 | 6275 / 5747 ms | — |
| A. scrollbar-gutter: stable | 6005 / 5738 ms | ❌ 无效，视口宽度变化非主要失效源 |
| **B. content-visibility: auto（论文 201 个块）** | **1909 / 1722 ms** | ✅ **降 ~70%，唯一有效手段** |
| C. contain: layout paint（容器级） | 5696 / 5857 ms | ❌ 无效，隔离不了全文档样式重算 |
| D. A+B+C 组合 | 1903 / 1741 ms | 与单独 B 持平，A/C 零贡献 |
| 基线（漂移检查） | 5966 / 5780 ms | 确认效果真实 |

结论：`content-visibility: auto` 让屏幕外块跳过强制重算，确立为施工核心；A/C 方案否决。
施工风险提示：contain-intrinsic-size 是占位估算，影响滚动高度/锚定与远离屏块的 scrollIntoView 落点；对齐高亮若依赖离屏块的几何位置会偶发偏移——需回归划词/高亮/块跳转链路。
