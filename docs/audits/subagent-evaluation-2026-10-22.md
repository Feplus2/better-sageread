# 子代理评估（P2）：先看 Harness 怎么做，再决定 SageRead 要不要

> 调研对象：本机 DeepSeek Harness 的 subagent 相关包（dsh-subagent / dsh-tool-subagent / spawn / fork / tool-subagent-control）· 日期 2026-10-22

## 1. Harness 的 subagent 是什么形态

| 组件 | 职责 |
|---|---|
| `dsh-subagent` | 委派 seam：服务 + 具名 provider + 统一生命周期（启动/消息/容量/父子/释放）。本地 spawn/fork 子级**可继续**（持久子会话）；ACP/Codex/Claude 等外部子级一次性执行 |
| `dsh-tool-subagent` | 面向模型的委派工具：立即返回子会话 ID，完成时父级收到结算通知 |
| `dsh-subagent-spawn-in-process` / `fork-in-process` | 进程内后端：spawn 全新状态、fork 继承已完成轮次内容（都保留可继续会话） |
| `dsh-tool-subagent-control` | `send_message` / 中断 / `list_agents` 等控制面 |

关键参数/约束（来自 README）：

- **深度**：`maxDepth` 默认 1（只允许直接子代理）；深度 0 禁止委派。
- **容量**：`maxActiveSubagents` 默认 8（每棵 activation 树）；容量满拒绝新接纳，不排队。
- **结算**：父级投递模式会在子级完成后追加一条 user-role 状态通知；不调用工具也会收到。
- **能力/权限**：子代理的权限范围在启动时固定，内部不能扩权；需要审批的操作自动拒绝。
- **持久化限制**：驻留与 inbox 仅限进程内；没有跨进程 parent mailbox；外部子级一次性执行。
- **token 影响**：每个结算 activation 给父级加一条通知；子级自己承担其上下文成本。

## 2. SageRead 是否需要

### 现有证据
- 单 agent 已能完成深度考证（probe-deep-research 5–7 步）、三文档对比（probe-cross-doc-3）、多图对比；
- 阅读类任务普遍短（3–20 秒、20–150k token），没有撞上下文上限；
- 跨库检索已在单 agent 内落地（书库 fan-out + RRF），无需并行子代理也能覆盖。

### 子代理可能带来的收益
- **上下文隔离**：超长多文档综述（10+ 篇）时，子代理只回传结论，父上下文更干净；
- **并行 fan-out**：多篇论文/多本书并行取证，缩短墙钟时间；
- **可继续研究任务**：把「帮我持续调研这个主题」变成可追加消息的后台任务。

### 成本
- UI 与状态：子会话列表、继续/中断、结算通知展示；
- 基础设施：容量、生命周期、权限、持久化；跨重启需要额外设计；
- 评测：多一个「委派是否比单 agent 更好」的维度，题库与判分要扩；
- 风险：模型把简单任务也委派出去，反而变慢/变贵。

## 3. 结论（暂决定）

**P2 不实现子代理，保留为 P3 选项。** 理由：当前单 agent 在能力探针与分桶 A/B 中已达标，没有证据表明子代理能解决现存失败模式；引入成本（UI/生命周期/权限/评测）远高于当前收益。

如果将来出现明确信号（例如用户开始做 10+ 篇文献综述、单轮上下文频繁逼近上限、或需要后台长任务），再按最小形态启动：

1. 只做 **one-shot spawn**（子级一次性执行、父级收结算通知），不做可继续/冷恢复；
2. 只允许 central 助手委派，深度固定 1、容量固定 2；
3. 场景限制在「多文档并行取证/长综述」，并在评测里加一条对照：单 agent vs 委派。
